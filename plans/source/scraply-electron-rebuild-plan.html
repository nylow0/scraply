1. Target outcome

Scraply is a ChatGPT-like desktop workspace dedicated to universal project ideation. It is not limited to startups: a thread may target software, research, mathematics, ecology, competitions, content, personal systems, business, experiments, or any other domain.

  • Windows-first Electron application with an installer and portable build.
  • Backend starts and stops automatically with Electron; no terminal is needed.
  • Dark, polished conversation UI with a persistent thread sidebar.
  • One-question-at-a-time intake that becomes a confirmed project brief.
  • Selectable orchestrator, worker, and idea-generation models.
  • Six parallel research streams with visible progress and readable reports.
  • Orchestrator reflection loops that can request targeted follow-up research.
  • Batch idea generation, cross-thread duplicate detection, scoring, buckets, ratings, and deeper branches.
  • Private local data and a private GitHub source repository.

Required environment

The rebuild requires one external service credential:

EXA_API_KEY=...

Development reads C:\Business\scraply\.env. The packaged app imports those values into Electron's protected local settings on first run and also provides a settings screen for replacing them. The file is never committed or packaged.

Explicit removals

  • Remove Google embeddings and every Google environment variable.
  • Remove the current browser-first SvelteKit product shell.
  • Remove the requirement to manually start a development server.
  • Do not require Docker, Python, SearXNG, or a paid search provider beyond the verified Exa account.
  • Do not expose raw JSON as a user-facing report.

3. Product experience

3.1 First launch

  1. Electron acquires a single-instance lock and starts the local service.
  2. Startup validates Exa without revealing the key.
  3. The app records whether Codex is installed and authenticated, then loads its available model IDs.
  4. After both required checks pass, the user enters the workspace.

3.2 Workspace layout

  • Left sidebar: New research button, searchable thread history, status, rename, archive, and delete.
  • Main conversation: assistant questions, user answers, brief review, research events, reports, and idea batches.
  • Composer: multiline input, submit, stop, retry, and context-aware suggested replies.
  • Research drawer: six live stream lanes, search counts, current task, costs, errors, and follow-up requests.
  • Idea workspace: bucket tabs, filters, score details, ratings, comparison, and deeper-dive actions.

3.3 Conversation intake

Ask one question at a time. Persist every answer immediately and allow Back, Edit, Skip optional, and Resume.

  1. What are we trying to generate ideas for?
  2. What is the broad theme or area, and what is your rough description?
  3. What would make an idea good in this context?
  4. What final output do you want?
  5. Who or what decides whether this succeeds?
  6. Why do you want to do this, and what main reward matters?
  7. What is the deadline or ideal window, and how much time is available each week?
  8. What skills, tools, resources, people, or data are available?
  9. What must be avoided?
  10. What decision must be made at the end?

After the required questions, offer optional questions individually:

  • safe versus weird/high-upside balance;
  • existing examples or problems to inspect;
  • specific research requirements;
  • important scoring criteria;
  • anything material that is still missing.

3.4 Brief confirmation

Generate an editable brief containing:

  • project name, theme, and description;
  • desired output and success definition;
  • constraints, resources, and avoid list;
  • research needs and final decision;
  • deadline, available effort, and idea-style preference.

The user must confirm or edit the brief before any research cost is incurred.

3.5 Run configuration

Present a focused setup step after the brief:

  • orchestrator provider: Codex;
  • orchestrator model;
  • research worker model;
  • idea-generation provider and model;
  • ideas requested and batch size;
  • maximum follow-up rounds;
  • per-stream search result and page limits;
  • parallelism and maximum estimated spend;
  • automatic plan publishing on or off.

Save named presets while keeping sensible defaults for a one-click run.

4.1 Process boundary

  • Run the backend in an Electron utility process so a model or parsing crash cannot take down the UI.
  • Bind any HTTP transport to 127.0.0.1 on an ephemeral port with a per-launch bearer token.
  • Prefer typed IPC for renderer commands and Server-Sent Events for streaming run events.
  • Set contextIsolation: true, nodeIntegration: false, and a strict Content Security Policy.
  • Electron owns startup, health checks, restart-once recovery, graceful shutdown, and stale-job recovery.

4.3 Model adapters

Codex

  • Detect Codex locally and require a compatible authenticated installation.
  • Before implementation, verify the installed Codex version's supported non-interactive and structured-output contract.
  • Spawn the executable directly without a shell, use an isolated working directory, stream structured events, and support cancellation.
  • Use Codex for orchestrator, research, synthesis, and idea-generation roles.
  • Never assume undocumented CLI flags. Gate the adapter behind an automated compatibility probe.

4.4 Packaging

  • Use Electron Builder with NSIS and portable Windows targets.
  • Bundle compiled renderer and backend assets; do not bundle development sources, secrets, or local databases.
  • Write mutable data under Electron's userData directory.
  • Include a first-run health screen and an in-app “Open data folder” action.
  • Add crash-safe updates later; automatic update infrastructure is not required for the first usable release.

5. Research and idea workflow

5.1 Canonical research streams

StreamMissionExpected evidence
LandscapeMap topic state, key concepts, constraints, and current approaches.Definitions, current methods, trends, and limiting conditions.
ExemplarsFind related people, projects, products, papers, demos, and entries.Concrete examples, what worked, and what has already been attempted.
Pain and GapsFind complaints, missing pieces, weak points, and unsolved problems.Direct unmet-need signals and recurring failure modes.
ResourcesFind usable datasets, APIs, libraries, tools, communities, and methods.Accessible building blocks with constraints and licenses.
AnalogiesFind adjacent fields solving similarly shaped problems.Transferable patterns and non-obvious combinations.
EvaluationFind rubrics, benchmarks, judging criteria, and quality signals.Ways to distinguish an exciting idea from a merely plausible one.

5.2 Worker loop

  1. Orchestrator turns the confirmed brief into stream-specific subquestions.
  2. Six workers start concurrently, one per canonical stream.
  3. Each worker searches Exa, fetches bounded page content, and extracts source-linked claims.
  4. Each worker writes a readable semantic HTML report and a structured evidence index.
  5. Orchestrator reviews all reports against an explicit coverage rubric.
  6. If evidence is weak, the orchestrator sends a targeted follow-up task only to the relevant worker.
  7. Stop when coverage is sufficient or the configured round, time, search, or spend cap is reached.
  8. Preserve partial reports and clearly label failed or uncertain streams.

5.3 Exa adapter

  • Use POST https://api.exa.ai/search with x-api-key.
  • Request search results and bounded text contents together when possible.
  • Normalize title, canonical URL, publication date, author, text, and stream/query provenance.
  • Cache normalized results by query and options to avoid paying twice for retries or resumed jobs.
  • Deduplicate canonical URLs across all six streams while retaining which streams requested them.
  • Apply per-stream and global concurrency limits, exponential backoff, and clear quota errors.
  • Never expose the Exa key to the renderer or logs.

5.4 Stream report format

Every stream returns semantic HTML with:

  • brief summary;
  • what was researched;
  • key findings;
  • useful examples and linked sources;
  • opportunities noticed;
  • weak spots and uncertainty;
  • suggested next search.

Sanitize model-authored HTML before storage and rendering. Optionally publish a stream or composite report with C:\Business\planning\publish-plan.cmd <path-to-fragment.html> when the command is available.

5.5 Idea generation

  1. Build a compact evidence pack from the brief, synthesis, stream reports, and user preference history.
  2. Generate ideas in batches through distinct creative lenses: direct gaps, analogies, combinations, constraint relaxation, and inversion.
  3. Reject near-duplicates across the entire workspace using provider-supported embeddings if verified; otherwise use local BM25/token similarity plus a model duplicate critic.
  4. Keep relevance, novelty, evidence strength, feasibility, demand, and saturation as separate axes.
  5. Assign presentation buckets rather than one destructive weighted rank: strong fit, creative outlier, safe bet, and needs evidence.
  6. Let the user compare, rate, pin, reject, export, or open a deeper research branch from any idea.

7. Interface system

7.1 Visual direction

  • Near-black canvas, charcoal surfaces, restrained desaturated green accent, and no purple gradients.
  • Geist or Satoshi for UI text and Geist Mono for model names, costs, and technical state.
  • Thin separators and negative space instead of a wall of rounded cards.
  • Soft elevation only for overlays, menus, and the floating composer.
  • Motion limited to transform and opacity; honor reduced-motion preferences.

7.2 Required UI states

  • first-run setup and key-validation states;
  • empty thread workspace with a clear new-thread action;
  • question typing, submitted, editing, and validation-error states;
  • brief draft, changed, confirmed, and stale states;
  • model catalog loading, unavailable, and changed states;
  • queued, running, reflecting, follow-up, completed, partial, failed, cancelled, and resumable research states;
  • empty, loading, populated, duplicate-dropped, and generation-failed idea states;
  • inline provider/quota errors with retry and settings actions.

7.3 Accessibility and responsiveness

  • Full keyboard operation, visible focus, semantic controls, and screen-reader progress announcements.
  • Sidebar collapses below desktop width; research drawer becomes a full-height sheet.
  • Composer remains reachable without covering the latest message.
  • Score visualizations include text values and do not rely on color alone.

8. Security, privacy, and operational rules

  • Keep the app local-only; do not add analytics, telemetry, accounts, or cloud sync.
  • Never send user data anywhere except the local Codex model path and Exa searches.
  • Redact keys and authorization headers from logs, errors, exports, reports, and crash dumps.
  • Use Electron safeStorage for imported secrets and expose only validation state to the renderer.
  • Validate all IPC payloads with shared Zod schemas.
  • Do not enable arbitrary renderer shell execution or unrestricted filesystem access.
  • Sanitize all model-authored HTML before display.
  • Use explicit cancellation and caps for model calls, Exa requests, follow-up loops, and report publishing.
  • Back up the SQLite file before migrations and provide an in-app export.

10. Implementation phases

Phase 0 — Destructive reset and proof spikes

  • Archive the old implementation outside the new source tree.
  • Verify Codex authentication, model listing, and structured-response behavior.
  • Retain the passing Exa live probe as an opt-in integration test.
  • Probe the installed Codex CLI and freeze a tested adapter contract; keep Codex disabled if compatibility fails.
  • Scaffold Electron, Svelte, preload, backend utility process, SQLite, and tests.

Gate: packaged shell opens, backend starts automatically, both keys validate, model list loads, and local persistence survives restart.

Phase 1 — Conversation and intake product

  • Build sidebar, new thread, message stream, composer, and one-at-a-time intake.
  • Implement editable brief generation and confirmation.
  • Implement model/run configuration and presets.

Gate: a fresh user can move from New Thread to a confirmed brief and configured run without touching a terminal.

Phase 2 — One-stream vertical slice

  • Run one stream through plan, Exa search, extraction, report, orchestration review, and targeted follow-up.
  • Render progress in the conversation and research drawer.
  • Support cancellation, retry, partial results, and crash recovery.

Gate: one stream produces a useful cited HTML report from the Electron UI.

Phase 3 — Six-stream research

  • Add the six canonical workers and deterministic concurrency/budget accounting.
  • Add orchestrator coverage review and selective follow-up rounds.
  • Add composite synthesis, report browsing, and optional plan publishing.

Gate: all six reports remain readable and useful, partial failures do not erase successful work, and caps cannot be exceeded.

Phase 4 — Idea workspace and deeper branches

  • Add batched idea generation, dedup, separate scores, buckets, comparison, ratings, and exports.
  • Add deeper-dive branches that inherit the brief, selected idea, ancestor reports, and user preferences.
  • Add Codex role-specific model selection where the validated adapter supports it.

Gate: ideas are genuinely distinct, evidence-linked, actionable, and improve after user ratings.

Phase 5 — Product hardening and private delivery

  • Run Electron security review, accessibility pass, responsive pass, and long-run cancellation tests.
  • Build NSIS and portable artifacts and test on a clean Windows account.
  • Create and verify the private GitHub repository and CI.
  • Write a short user guide inside the app, not as a pile of external setup documents.

Gate: install, enter two keys, start a thread, complete research, generate ideas, restart, and resume—all without a terminal.

11. Final acceptance criteria

  1. The installer launches a real Electron app and automatically manages its backend.
  2. The only required secret is EXA_API_KEY.
  3. Google code, variables, documentation, and dependencies are absent.
  4. The first screen is a useful dark conversation workspace, not an empty developer dashboard.
  5. New Thread immediately starts the one-at-a-time universal intake.
  6. Every answer, brief, run, report, idea, rating, and branch survives restart.
  7. Model selectors are populated from Codex model discovery; unavailable models cannot be selected silently.
  8. Codex is detected and compatibility-tested before research starts.
  9. Exactly six canonical research streams run with visible progress and selective follow-up work.
  10. Exa search failures and quota errors are explicit, retryable, and never fabricated as successful research.
  11. Every stream and composite report is readable sanitized semantic HTML with linked sources.
  12. Idea batches are deduplicated workspace-wide and keep separate quality axes.
  13. Users can rate, compare, export, and dive deeper into ideas entirely from the desktop UI.
  14. Cancellation, budget caps, partial failures, crash recovery, and resume are tested.
  15. The GitHub repository is verified private and contains no secrets or user data.
  16. Automated unit, integration, Electron end-to-end, packaging, and clean-install smoke tests pass.

12. Known risks and honest constraints

  • Codex model IDs and structured-output quality must be live-tested; selectors cannot rely on remembered names.
  • The exact Codex non-interactive interface must be probed against the installed version before it is treated as supported.
  • Exa is verified now but still has external quotas and availability; caching and clear quota UX remain necessary.
  • Electron plus native SQLite packaging requires ABI-aware builds and clean-machine installer tests.
  • Generating hundreds of strong ideas in one call will degrade quality; batches and dedup are mandatory.
  • A polished UI does not rescue weak research. Phase gates must judge report and idea quality, not only passing code.
